# Phase-0 tiered-storage contract review

Reviewed against worktree commit `4b3c499842ee` on `feat/tiered-workspace-storage`. The two proposed contracts were not edited. Findings are ordered by severity and by how early they block a safe implementation.

1. **[BLOCKER] Archive and destroy observations are forgeable by the unprivileged cell agent.**

   The design treats the root helper as the boundary that proves host actions, but the Manager authenticates only the cell agent's mTLS request (`vcs/internal/controlplane/http.go:78-98`). The agent receives ordinary JSON from the helper, checks only the plan generation/release and assignment identifiers, then posts it under the cell credential (`vcs/internal/cellagent/agent.go:92-103`, `vcs/internal/cellagent/agent.go:123-141`, `vcs/internal/cellagent/agent.go:228-249`). New fields such as `ArchiveSealed`, `DestroyProofSHA256`, or `released` would pass those checks without proving that the helper produced them. A compromised agent can therefore invent a seal, induce the Manager to sign `DESTROY`, invent destruction and release observations, and leave the Manager believing that S3 is canonical while the archive is invalid and cell data still exists. Hashing a typed result does not authenticate its producer (`docs/tiered-storage/identity-lifecycle-and-capacity.md:121-152`). The contract needs a root-helper-held attestation key (or an equivalent authenticated local channel whose result the Manager can verify), and the attestation must bind the exact signed plan digest, plan generation, volume, epoch, placement tuple, operation, result, and replay identity.

2. **[BLOCKER] “Authority epoch” currently names two different values; the proposed rename does not unify them.**

   `AuthorityGeneration` is a Manager-owned `uint64` pinned into grants and enrollments (`vcs/internal/controlplane/types.go:152-180`, `vcs/internal/volumecap/volumecap.go:55-60`, `vcs/internal/volumecap/volumecap.go:231-245`). Separately, every authority process generates a random 16-byte protocol epoch at startup (`vcs/internal/volumeserver/session.go:30-34`, `vcs/internal/volumeserver/session.go:186-223`), and the frozen authority wire stamps and checks those bytes (`vcs/internal/authorityrpc/server.go:41-48`; `COMPATIBILITY.md:65-68`). The spec calls renaming the integer “existing v1 behavior, unchanged in mechanism” and says there is exactly one counter (`docs/tiered-storage/identity-lifecycle-and-capacity.md:28-35`). That is false today. If the process epoch becomes a deterministic encoding of the integer, an accidental same-generation process restart reuses an epoch after losing sessions and replay slots, allowing clients to mistake a new process for the old exact-replay domain. If it remains random, there are still two epoch identities. The contract must name both values or define how a new authority process atomically reserves the next durable integer before it can listen, including crash and manual-start behavior.

3. **[BLOCKER] The stated pre-seal wake abort cannot return to READY at the same epoch after quiesce.**

   Quiesce kills the authority and only then checks strict membership (`docs/tiered-storage/identity-lifecycle-and-capacity.md:101-120`), while the abort path says to restart it at the same epoch (`docs/tiered-storage/identity-lifecycle-and-capacity.md:158-160`). Current process startup always creates a fresh random wire epoch (`vcs/internal/volumeserver/session.go:199-223`). Worse, if the membership check finds a live record, the replacement authority refuses to start unless an operator clears it (`vcs/cmd/portablefs-authority/main_linux.go:168-182`). Only an authenticated `CleanDetach` from the exact live session removes a record; the authority cannot inspect the remote kernel (`vcs/internal/volumeserver/visibility.go:743-784`, `docs/failure-modes.md:170-191`). Reusing the old integer would not recover the lost sessions or exact replies either. Membership must be drained and proven empty while the old authority is alive, before it is killed. Once killed, abort needs a new fenced epoch and the normal prior-mount proof; “same epoch” is not safe.

4. **[BLOCKER] Epoch-bearing endpoint names conflict with the helper's immutable-assignment rule.**

   The new endpoint changes on every epoch, including a within-cell fencing restart (`docs/tiered-storage/identity-lifecycle-and-capacity.md:28-35`, `docs/tiered-storage/identity-lifecycle-and-capacity.md:50-54`). Yet helper v2 is specified to permit changes only to the two quota values and keep every other assignment field immutable (`docs/tiered-storage/identity-lifecycle-and-capacity.md:293-299`). Current enforcement explicitly treats `AuthorityID` and `AuthorityServerName` as immutable while allowing a generation increment after `FENCE` (`vcs/internal/cellhelper/reconciler.go:98-104`, `vcs/internal/cellhelper/reconciler.go:173-180`). A normal fence from epoch `e` to `e+1` would therefore be rejected. The contract must either keep a stable placement endpoint across within-placement epoch changes or add a narrowly checked endpoint transition tied to the exact `FENCE` absence proof.

5. **[BLOCKER] Retaining the service account makes a fresh same-cell UID impossible for the same VolumeID.**

   Destroy removes the sysusers file but deliberately retains the persistent account (`docs/tiered-storage/identity-lifecycle-and-capacity.md:135-143`), while a later wake on the same cell must allocate a fresh service UID/GID (`docs/tiered-storage/identity-lifecycle-and-capacity.md:36-39`, `docs/tiered-storage/identity-lifecycle-and-capacity.md:164-170`). Current account names are deterministic functions of VolumeID (`vcs/internal/cellhost/host_linux.go:345-361`). Provisioning then requires that this name own exactly the newly signed UID/GID and that the numeric IDs resolve back to that name (`vcs/internal/cellhost/host_linux.go:364-389`). The retained old account causes every later fresh-UID assignment for that VolumeID on that cell to fail. Incarnation identity must enter the username, or destruction must remove the account with a separately proved safe reuse policy.

6. **[BLOCKER] A wake racing archive steps 3-5 cannot be represented by the proposed single `Placement`.**

   At the ARCHIVED commit, the old placement remains so it can receive `DESTROY` and `RELEASE` (`docs/tiered-storage/identity-lifecycle-and-capacity.md:129-152`). The spec then says a wake after that commit proceeds as a restore, whose first actions allocate a fresh placement (`docs/tiered-storage/identity-lifecycle-and-capacity.md:158-168`). The v2 schema has only one `Placement *Placement` (`docs/tiered-storage/identity-lifecycle-and-capacity.md:214-230`), matching the current one-cell flat record (`vcs/internal/controlplane/types.go:104-130`) and one-plan-per-current-cell emission (`vcs/internal/controlplane/manager.go:581-607`). Overwriting it loses the old tuple and destroy proof; retaining it leaves nowhere to record the restore tuple. The contract must require release of the old placement before restore placement, or add a separate retiring-placement record and define both plans and observations during the overlap.

7. **[BLOCKER] Clearing placement is incompatible with retained terminal mount enrollments.**

   Quiesce revokes active enrollments, but terminal enrollment records intentionally remain for 15 minutes (`vcs/internal/controlplane/manager.go:1044-1053`, `vcs/internal/controlplane/manager.go:1156-1166`; `docs/hosted-control-plane.md:51-59`). Current validation binds every enrollment, including revoked and closed ones, to the volume's current cell and authority identity; only the active case adds generation equality (`vcs/internal/controlplane/types.go:419-470`). The v2 volume moves those binding fields into a nullable placement and says only that a placement-free volume has no *active* enrollments (`docs/tiered-storage/identity-lifecycle-and-capacity.md:246-252`). After RELEASE there is no placement against which terminal records can validate. DESTROYED also drops the volume record while such enrollments may remain. The v2 validator must define historical binding validation, immediate terminal-record removal, or a placement tombstone; omitting the rule breaks load-time state validation.

8. **[BLOCKER] The single tombstone map does not define release across repeated same-cell incarnations.**

   The proposed state keeps one tombstone per VolumeID and says every later `RELEASE` for a tombstoned volume is an idempotent no-op, while also allowing a newer assignment for that VolumeID (`docs/tiered-storage/identity-lifecycle-and-capacity.md:299-309`). After incarnation `e` is tombstoned and incarnation `e+1` returns to that cell, the legitimate `RELEASE(e+1)` is “a later RELEASE for a tombstoned volume” under the written rule and may fail to remove the live assignment. Conversely, checking the tombstone before the current assignment could make a stale `RELEASE(e)` look successful while `e+1` remains assigned. Current reconciliation validates immutable assignment continuity before host work and rejects disappearing assignments (`vcs/internal/cellhelper/reconciler.go:90-113`), so branch order matters. Define exact matching: a RELEASE may consume only the current assignment with the same epoch, tuple, and destroy proof; no-op replay is allowed only when no current assignment exists and the plan matches the stored tombstone exactly. A newer assignment must not erase the replay fence.

9. **[MAJOR] The destroy proof has no canonical, crash-stable definition.**

   Host work currently occurs before the helper atomically saves its durable assignment (`vcs/internal/cellhelper/reconciler.go:130-157`, `vcs/internal/cellhelper/state.go:91-132`). A crash after deleting the tree or config but before saving the destroy result will rerun the operation. The spec says only “SHA256 over the typed result” and does not list the type, encoding, identity fields, or whether “already absent” hashes identically to “removed on this attempt” (`docs/tiered-storage/identity-lifecycle-and-capacity.md:132-149`). If action history enters the hash, retry produces a different value and RELEASE can never match; if identity does not enter it, an old proof can authorize the wrong incarnation. Specify a canonical post-condition record bound to cell, VolumeID, epoch, full placement tuple, signed plan digest/generation, and fixed derived targets. Hash postconditions, not whether this attempt performed each removal.

10. **[BLOCKER] Archive object keys are reused after an abort, but no rule fences a stale uploader or enforces immutability.**

   Object keys contain only VolumeID and sealed epoch (`docs/tiered-storage/pack-format.md:82-86`). A pre-commit wake aborts at the same epoch and garbage-collects forming objects (`docs/tiered-storage/identity-lifecycle-and-capacity.md:158-160`); a later archive in that epoch therefore targets the same keys. Neither spec requires the old archiver to be stopped and proved absent, gives an upload-attempt ID, records S3 version IDs, nor requires conditional create. A stale multipart completion can overwrite an object after GC or after a newer attempt sealed it. Local plan anti-equivocation only rejects a different payload at the same plan generation (`vcs/internal/cellhelper/reconciler.go:86-89`); it does not fence an already launched network process. Use never-reused attempt keys, prove the archiver unit absent on phase exit, seal immutable object versions, and make GC target exact attempt/version identities.

11. **[MAJOR] Archive success has no durable cell-side replay record.**

   An old-plan observation is ignored when the Manager has already advanced the cell plan (`vcs/internal/controlplane/manager.go:362-375`). Plan refreshes advance generation even without a desired-state change (`vcs/internal/controlplane/manager.go:521-570`). The helper's durable assignment currently retains only plan/application facts (`vcs/internal/cellhelper/reconciler.go:27-48`), and the proposed v2 additions mention quotas and tombstones but no `ArchiveSealed` record (`docs/tiered-storage/identity-lifecycle-and-capacity.md:290-309`). If upload completes and the archiver or helper dies before the Manager accepts that observation, reconciliation has no specified source from which to reproduce the exact manifest digest, object versions, and totals. Persist the sealed result under the helper boundary before reporting it, then make `Observe` replay it byte-for-byte across helper, agent, and plan-generation changes.

12. **[MAJOR] `ArchiveTo` and `RestoreFrom` contradict the helper's no-network-selected-input claim.**

   Current cell plans accept no path, command, executable, unit text, or environment from the network (`vcs/internal/cellplan/plan.go:1-4`), and host paths derive from root-pinned configuration plus validated IDs (`vcs/internal/cellhost/host_linux.go:3-6`, `vcs/internal/cellhost/host_linux.go:82-95`). The proposal adds a Manager-selected object-key prefix and Manager-selected manifest/pack keys, then claims this preserves the same rule (`docs/tiered-storage/identity-lifecycle-and-capacity.md:278-288`). Object keys are network-selected storage paths, and the helper would cause privileged unit creation and credential use against them. Define a strict key grammar and derive keys locally from a root-pinned bucket/prefix plus `(VolumeID, epoch, attempt)`; plans should carry digests and identities, not arbitrary remote paths.

13. **[MAJOR] The archiver is not confined to read-only access to canonical XFS.**

   The current architecture forbids sidecars and operators from mutating the tree behind the authority because such writes bypass authorization and coherence (`docs/xfs-authority-architecture.md:135-137`). The new archiver runs as the same UID as the authority, and the spec gives it network credentials but says nothing about a read-only bind, filesystem namespace, syscall policy, unit restart policy, or how `SERVE`/`DESTROY` proves it has exited (`docs/tiered-storage/identity-lifecycle-and-capacity.md:121-128`). Current authority drop-ins bind the volume read-write (`vcs/internal/cellhost/host_linux.go:465-479`). An archiver bug or stale process can mutate XFS during export or after the seal, invalidating the one-representation claim. The unit contract must pin read-only XFS access and prove the unit/cgroup absent before abort, commit-to-destroy, or authority restart.

14. **[BLOCKER] The restore correctness contract is delegated to a file that does not exist.**

   Both lifecycle references point to `docs/tiered-storage/restore-mode.md` (`docs/tiered-storage/identity-lifecycle-and-capacity.md:9-10`, `docs/tiered-storage/identity-lifecycle-and-capacity.md:175-181`), but that file is absent. The remaining two-line rule says a hydration bit becomes durable before a write lands and then treats the bit as proof that XFS is canonical (`docs/tiered-storage/identity-lifecycle-and-capacity.md:89-93`). It does not define the required ordering among base read verification, XFS write, file `fsync`, hydration-map write, map `fsync`, user mutation, and mutation reply. Nor does it cover partial writes, truncate, hole punch, rename/unlink during background drain, hardlinks, or failure after the Manager commits READY. Current write and `fsync` acknowledgements have exact XFS meanings (`docs/xfs-authority-architecture.md:107-124`); restore mode cannot change them implicitly. Phase 0 is incomplete until the missing contract specifies these transitions and crash points.

15. **[BLOCKER] The proposed `fstatfs` measurement contradicts the current filesystem contract and can multiply-count cell use.**

   The spec says `fstatfs` on a project directory reports that project's quota and derives used blocks from `f_blocks - f_bfree` (`docs/tiered-storage/identity-lifecycle-and-capacity.md:319-327`). Current architecture and failure contracts state the opposite: `statfs` keeps ordinary cell-wide XFS physical-capacity meaning, while quota APIs report per-volume entitlement (`docs/xfs-authority-architecture.md:438-444`, `docs/failure-modes.md:210-217`). Summing one cell-wide value for every placement multiplies the same usage by the placement count. Although provisioning currently compares `fstatfs` totals to signed quota (`vcs/internal/cellhost/host_linux.go:433-461`), that existing disagreement is not evidence that per-project used space is available. Phase 0 must select and prove a real per-project usage source, most likely a narrow privileged quota query, and reconcile the contradictory current code/docs before building admission on it.

16. **[BLOCKER] Reservation-free measured admission over-admits even with perfectly fresh observations.**

   The formula explicitly has “No reservation term” (`docs/tiered-storage/identity-lifecycle-and-capacity.md:324-327`). Suppose measured use is zero, capacity is 100, and two creates with a provision floor of 60 serialize through the Manager before either cell observation arrives. Each transaction sees zero measured use and admits, yielding 120 of promised initial placement. Current code closes this window by durably adding quota allocation in the same create transaction and validating the sum against capacity (`vcs/internal/controlplane/manager.go:194-230`, `vcs/internal/controlplane/types.go:563-567`). Removing both the sum and any pending-placement reservation removes that invariant. Admission needs a durable charge for every placed-but-not-yet-measured create/restore, released only when a sufficiently new observation supersedes it.

17. **[MAJOR] Observation freshness and offline-cell admission are unspecified.**

   Used observations have timestamps in the proposed placement, but the formula does not say how old they may be or whether any missing/error observation makes the cell ineligible (`docs/tiered-storage/identity-lifecycle-and-capacity.md:221-229`, `docs/tiered-storage/identity-lifecycle-and-capacity.md:319-336`). Current liveness is a separate in-memory heartbeat check (`vcs/internal/controlplane/manager.go:171-178`), and current placement excludes only quarantined cells, not degraded, unknown, or stale ones (`vcs/internal/controlplane/manager.go:195-205`). A cell can retain durable `HEALTHY` and old low usage while offline. Require a fresh heartbeat at the current plan generation plus a fresh successful usage observation for every current placement; otherwise admission must fail closed. Define how one missing volume measurement affects the cell total.

18. **[MAJOR] Manifest logical totals are not exact restore-capacity inputs.**

   Admission calls `LogicalBytes`/`LogicalInodes` exact sizing (`docs/tiered-storage/identity-lifecycle-and-capacity.md:324-327`), but the pack records logical file sizes and sparse extents (`docs/tiered-storage/pack-format.md:51-60`). XFS consumption also includes block rounding, directory blocks, symlink storage, and other metadata; sparse holes consume no data blocks, hardlinks must count one inode/data allocation, and a large sparse logical file can exceed physical use by orders of magnitude. Current admission and quota checks reason in XFS blocks/inodes, not summed `st_size` (`vcs/internal/cellhost/host_linux.go:450-461`). Record sealed allocated-block and inode requirements under an explicit accounting algorithm, with headroom for restore-created metadata, rather than labeling logical totals exact.

19. **[MAJOR] The helper/agent/manager rollout cannot be backward-compatible as written.**

   Current helpers reject any state version other than 1 (`vcs/internal/cellhelper/state.go:17-18`, `vcs/internal/cellhelper/state.go:53-55`), and current plan verification accepts only the `v1.` token/domain and plan version 1 (`vcs/internal/cellplan/plan.go:24-29`, `vcs/internal/cellplan/plan.go:104-138`, `vcs/internal/cellplan/plan.go:141-145`). The new helper says it migrates v1 state to v2 on load, while rollout must work in both directions during helper -> agent -> manager deployment (`docs/tiered-storage/identity-lifecycle-and-capacity.md:290-312`). Once a v2 helper writes v2 state, rolling it back to the current helper fails immediately. The contract also does not say whether plan v2 changes the token prefix/signature domain or how a v2 helper accepts v1 envelopes. Specify dual-read/write timing, rollback limits, signature domain separation, and the exact gate that first writes v2 state.

20. **[MAJOR] New archive metadata has no bounds compatible with existing Manager, plan, and HTTP limits.**

   Pack count, object-key length, manifest size, entry count, and archive-result size are unbounded in both specs; packs merely shard above about 78 GiB (`docs/tiered-storage/pack-format.md:74-86`). Current signed plans allow 3 MiB payloads/4 MiB envelopes (`vcs/internal/cellplan/plan.go:24-28`, `vcs/internal/cellplan/plan.go:89-100`), helper/agent observations allow 4 MiB (`vcs/internal/cellagent/agent.go:203-225`), Manager HTTP bodies allow only 1 MiB (`vcs/internal/controlplane/http.go:418-432`), and a full Manager state record is capped at 64 MiB (`vcs/internal/controlplane/store.go:19-24`, `vcs/internal/controlplane/store.go:286-296`). `ArchiveRecord.PackObjects`, `ArchiveSealed.PackObjects`, and `RestoreFrom` can exceed different boundaries. Phase 0 needs one set of maxima and a bounded indirection scheme; it cannot rely on every consumer happening to accept the list.

21. **[BLOCKER] A manifest entry does not identify its parent, so the namespace cannot be reconstructed.**

   The manifest lists only `name` per entry and does not define whether it is a component, full path, parent index, or entry ID (`docs/tiered-storage/pack-format.md:45-60`). Current namespace identity is explicitly parent-token plus one raw component; host paths and client inode numbers are never accepted (`docs/xfs-authority-architecture.md:139-168`, `COMPATIBILITY.md:65-68`). Repeated names in different directories are normal. Add a canonical parent/entry graph (with root identity, topological ordering, duplicate-name rules, and cycle checks) using raw component bytes. Without it, two conforming readers can build different trees.

22. **[BLOCKER] Shared-frame chunk descriptors do not separate frame identity from file-slice identity.**

   Small files share one zstd frame and use `innerOffset`, but the chunk tuple has only one `uncompressedLen`, one digest, and one `xxh64lo32` (`docs/tiered-storage/pack-format.md:25-43`, `docs/tiered-storage/pack-format.md:57-60`). It is undefined whether those fields cover the complete decompressed frame or the individual file slice. Multiple entries referencing one frame need a canonical frame record (pack offset, compressed length, raw/compressed flag, frame uncompressed length, frame checksums) plus a separate slice record (inner offset, byte length, content mapping). Otherwise readers cannot agree on what to hash or how much data belongs to a small file, and corruption outside one slice may go unchecked.

23. **[BLOCKER] Sparse-file chunks have no logical offsets, and “one chunk” conflicts with “holes are never stored.”**

   Files at most `chunkSize` are declared exactly one chunk, while sparse holes are never stored (`docs/tiered-storage/pack-format.md:20-23`). The chunk list has no file offset, logical band index, or extent reference (`docs/tiered-storage/pack-format.md:57-60`). For a sparse file with two data extents around a hole, a reader cannot tell whether the stored bytes include zeros, concatenate extents, or form separate chunks, nor can it place them without an ordering rule that binds chunks to extents. Current XFS semantics preserve both sparse layout and file bytes (`docs/xfs-authority-architecture.md:98-104`). Define chunking over logical offsets, the digest treatment of holes, and the exact mapping between each data extent and frame slice.

24. **[BLOCKER] Hardlink and content-dedup identities are unsafe for a monotone hydration map.**

   Hardlink members must become one inode, while byte-identical but unrelated files share the same chunk list (`docs/tiered-storage/pack-format.md:35-36`, `docs/tiered-storage/pack-format.md:51-60`, `docs/tiered-storage/pack-format.md:90-99`). A hydration bit keyed by path is wrong for hardlinks: one alias can be hydrated or written while another alias later replays base bytes onto the same inode. A bit keyed by chunk list/digest is wrong for deduplicated independent files: writing one file must not mark the other file's XFS chunk canonical. Current XFS supplies real hardlink identity and open-after-unlink semantics (`docs/xfs-authority-architecture.md:100-103`, `docs/xfs-authority-architecture.md:125-132`). The format and missing restore-mode contract need distinct content-object, restored-inode, and logical-chunk identities, with rename/unlink behavior and write/hydrate locking defined.

25. **[MAJOR] The raw-chunk exception defeats the advertised stock-zstd recovery property for ordinary packs.**

   Raw bytes may be inserted between zstd frames, and only the manifest locates them (`docs/tiered-storage/pack-format.md:37-43`). Stock `zstd -d` will stop at that non-frame data, so the property holds only for the subset of packs whose compression heuristic never selects raw. The verification test repeats that conditional subset (`docs/tiered-storage/pack-format.md:101-110`). Since raw selection depends on content, operators cannot count on the claimed disaster-recovery path for an arbitrary archive. Encode incompressible chunks as valid zstd frames containing raw blocks, or remove the stock-decoder claim and specify a standalone recovery scanner.

26. **[MAJOR] The multipart rule can create illegal S3 parts and the 78-GiB ceiling is computed from the wrong size.**

   Lifecycle says “part = chunk boundary,” and the format derives a roughly 78-GiB shard ceiling from 10,000 8-MiB chunks (`docs/tiered-storage/identity-lifecycle-and-capacity.md:121-126`, `docs/tiered-storage/pack-format.md:74-86`). Pack offsets and multipart parts are compressed-byte ranges, however. An 8-MiB logical chunk compressed below 5 MiB cannot be a nonfinal S3 multipart part; AWS requires every nonfinal part to be at least 5 MiB. Compression also means 10,000 parts do not imply a fixed 78-GiB object. Require each part to contain one or more complete frames, choose boundaries after compression subject to 5-MiB through 5-GiB part limits, and shard by actual compressed bytes plus the 10,000-part cap. See the official [S3 multipart limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html) and [CompleteMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html).

27. **[MAJOR] Checksum roles and the manifest seal disagree across the two specs.**

   The lifecycle `ObjectRef` gives every manifest and pack object both CRC64NVME and SHA-256 (`docs/tiered-storage/identity-lifecycle-and-capacity.md:232-239`), while the pack header lists pack digests only as CRC64NVME and per-chunk SHA-256/XXH32 (`docs/tiered-storage/pack-format.md:57-65`). The manifest also contains its own digest “of everything before it” without fixing whether the digest is in a footer, what bytes precede it, padding rules, or how unknown-version fields are handled. Current state and plan formats reject unknown fields and hash exact canonical payload bytes (`vcs/internal/controlplane/store.go:173-190`, `vcs/internal/cellplan/plan.go:89-98`). Define the byte-level manifest seal, whole-pack SHA-256 presence, frame/slice SHA roles, and whether CRC64NVME is only S3 transport/storage checking. AWS treats CRC64NVME as a full-object checksum for multipart objects, not a replacement for the content-addressed SHA identities described elsewhere ([AWS checksum documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)).

28. **[MAJOR] Ownership and ctime restoration cannot meet the stated identity/test contract.**

   The manifest stores source numeric uid/gid and uname/gname, but every restored incarnation receives a fresh service UID/GID (`docs/tiered-storage/pack-format.md:51-56`, `docs/tiered-storage/identity-lifecycle-and-capacity.md:164-174`). Current PortableFS requires every inode to be owned by that one per-volume service principal (`docs/xfs-authority-architecture.md:466-474`), and provisioning verifies the root against the fresh numeric IDs (`vcs/internal/cellhost/host_linux.go:442-449`). The spec does not say whether stored IDs are informational or projected, so readers can restore forbidden old host IDs. It also says ctime is preserved “as closely as permits” but asks the round-trip test to compare ns-times (`docs/tiered-storage/pack-format.md:90-109`); Linux does not provide an API to set arbitrary inode ctime, and restore operations change it. State exact projection rules and limit equality tests to fields the restorer can set, with ctime recorded only as archive metadata if desired.

29. **[MAJOR] Files-gateway eviction has an install race and no machine-checkable quiesce result.**

   The current gateway has GET/PUT session routes but no DELETE route (`vcs/cmd/portablefs-files/main.go:162-175`). Session installation dials the authority before taking the registry lock and then unconditionally installs the session (`vcs/cmd/portablefs-files/main.go:205-250`, `vcs/cmd/portablefs-files/main.go:251-284`). A DELETE can return between those stages and a pre-issued grant can install afterwards. The lifecycle merely calls DELETE on configured gateways and proceeds; its quiesce proof contains only authority absence and strict membership emptiness (`docs/tiered-storage/identity-lifecycle-and-capacity.md:101-120`). Add a per-volume gateway fence generation checked by PUT after dial and before install, make DELETE durably/convergently advance it, and include gateway-session absence (or a proof that authority shutdown makes the race irrelevant) in the step definition.

30. **[MAJOR] RESTORING convergence and READY commit order are not crash-defined.**

   The sequence says background drain becomes digest-verified, restore mode turns off, and the Manager transitions to READY, but it gives no ordering or replay token among those actions (`docs/tiered-storage/identity-lifecycle-and-capacity.md:175-183`). Current Manager transitions are observation-driven and every desired-state change bumps the signed plan generation (`vcs/internal/controlplane/manager.go:460-490`, `vcs/internal/controlplane/manager.go:1030-1035`); stale observations are ignored (`vcs/internal/controlplane/manager.go:362-375`). A crash after the authority disables restore mode but before READY, or after READY is committed but before the helper persists “mode off,” needs a deterministic next plan and observation. Define a durable local convergence record, what digest it verifies when user writes have changed the tree, an observation bound to the plan, and a Manager commit point after which SERVE can never re-enable base replay. Archive GC must wait for that exact committed proof.

31. **[MINOR] DESTROYED is described both as a terminal state and as absence of a record.**

   The lifecycle graph includes terminal `DESTROYED` (`docs/tiered-storage/identity-lifecycle-and-capacity.md:67-72`), the validator discusses a placement-free DESTROYED-pending record (`docs/tiered-storage/identity-lifecycle-and-capacity.md:246-252`), but deletion from ARCHIVED says to delete objects and “drop the record” (`docs/tiered-storage/identity-lifecycle-and-capacity.md:193-198`). Current `GetVolume` and enrollment validation distinguish a present volume from `ErrNotFound` (`vcs/internal/controlplane/manager.go:240-250`, `vcs/internal/controlplane/types.go:436-440`). Pick one durable API meaning, including idempotent retry/audit retention and how remaining receipts or terminal enrollments refer to a deleted volume.

## Disposition

The specs are not ready to freeze. Findings 1-8, 10, 14-16, 21-24 block a safe implementation because they permit false destruction/seal claims, epoch reuse, an unrestartable abort, lost cleanup identity, over-admission, or non-deterministic restore. The remaining major findings leave crash recovery, rollout, capacity measurement, and the shared pack format dependent on choices that different implementers can make differently.
